# zarr fixtures and encoding table

Status: done
Type: task
Blocked by: none

## What

Generate the zarr fixture set and the zarr encoding table (spec "Encodings" and "Fixtures").

- Python writes each fixture case as a v3 store (Python defaults: sharded and consolidated) and a v2 store into `tests/testthat/fixtures/zarr/`, plus unsharded, unconsolidated and per-compressor (zstd, blosc, gzip, none) v3 variants
- A generated zarr encoding table (alongside `.scratch/h5ad-io/encoding-table.md`) records, for every case and both versions, the dtype, codecs, fill value, attributes and layout Python writes, with a freshness test like the h5ad one
- Extend `h5_tree.py`/`expect_structurally_equivalent()` (or add zarr counterparts) so Structural equivalence can be checked between two zarr stores and between a zarr store and an h5ad file, ignoring chunk shape, codecs and shard layout
- Keep fixture size small (the h5ad set is the model)

## Acceptance criteria

- Fixtures and the encoding table are committed and regenerated by `scripts/regenerate-fixtures.sh`
- Structural equivalence helpers work for zarr stores, with tests on Python-written pairs (equal and deliberately different)
- `scripts/check.sh` passes

## Comments

2026-10-16: done.

- `tests/python/generate_zarr_fixtures.py` writes 169 cases (every h5ad case with a zarr equivalent, minus `bytes_scalar` and the HDF5-compression ones) as `v3` and `v2`, plus the variants `v3_unsharded`, `v3_unconsolidated` and `v3_zstd`/`blosc`/`gzip`/`none` for a few base cases.
  Element cases are written with `write_elem` (key `x`, not consolidated), whole objects with `anndata.io.write_zarr` (consolidated)
- The stores are committed as `tests/testthat/fixtures/zarr-fixtures.tar.gz` (packed by `pack_zarr_fixtures.py`), not as a directory tree, because `R CMD check` gives NOTEs for the hidden files (`.zarray`) and for paths over 100 bytes.
  Tests unpack it once with `zarr_fixture_dir()` / `zarr_fixture_path()` (`helper-python.R`).
  The stale unpacked `tests/testthat/fixtures/zarr/` left by this run is gitignored and Rbuildignored and can be deleted (the shell denied `rm`)
- `.scratch/zarr-io/encoding-table.md` is generated by `zarr_encoding_table.py` from the raw `zarr.json`/`.zarray` files, for both versions, and guarded by a freshness test
- `h5_tree()`/`expect_structurally_equivalent()`/`expect_all_equivalent()` now accept zarr store directories (`zarr_tree.py`, same node format as `h5_tree.py`), also between a store and an h5ad file.
  Chunks, codecs, shards, fill value and zarr format are not compared.
  The attribute `type` is only compared between two files of the same kind, because zarr stores only JSON types
- The h5ad encoding table was already stale (7 rows missing, the test failed), so it was regenerated here
- `__pycache__/` is now gitignored

Findings the next tickets need:

- Python writes a missing `raw` in zarr as a `null` Element (0-d bool array at `raw`), whereas h5ad has no `raw` node.
  The zarr writer (zarr-io/05) must write it too, and cross-format comparisons must expect this one extra node (see `test-zarr-fixtures.R`)
- zarr keeps rec-array field dtypes (v3 `struct` data type, v2 structured `dtype`, including `U` and `S` fields), unlike HDF5.
  This bears on ADR 0005 and the spec line "if zarr makes field dtypes easier to preserve, preserve them", for the human to settle in zarr-io/07
- `AnnData.write_zarr()` takes no dataset arguments in Python (`compressors`, `shards`), only the function `anndata.io.write_zarr()` does, which matters for the spec's `adata$write_zarr(store, ...)`
- Consolidated metadata is trusted by zarr readers, so edits to a consolidated store's child metadata are ignored
