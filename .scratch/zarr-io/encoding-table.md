# zarr encoding table

What Python anndata 0.13.4 (zarr 3.4.1) writes for every encoding case, as a v3 store and a v2 store.
It is the reference for the zarr writer layer (ADR 0007), next to the HDF5 table in `.scratch/h5ad-io/encoding-table.md`.

The observed block is generated from the fixtures in `tests/testthat/fixtures/zarr/` and a test checks it is current.
After changing a case, regenerate it with:

```sh
uv run --project tests/python python -I tests/python/zarr_encoding_table.py tests/testthat/fixtures/zarr .scratch/zarr-io/encoding-table.md
```

How to read the **On disk** column:

- v3 arrays: `data_type [shape] chunks <chunk shape>; codecs <codec chain>; fill <fill value>`
  - A `sharding(inner chunks ...)` codec means Python sharded the array (the default `auto_shard_zarr_v3`), and the `chunks` are then the shard shape
  - `bytes` is the array to bytes codec, `endian` is always little and omitted
- v2 arrays: `dtype [shape] chunks <chunk shape>; order; compressor; filters; fill <fill value>`
- A scalar has the shape `scalar`
- Groups list their members, and whole objects (`anndata_*`, `realistic*`) only list their Slots
- Attributes other than `encoding-type` and `encoding-version` are in the last column, as JSON
- Cases Python refuses to write are rows with `Python error`, as in the HDF5 table

Whole objects are written with `write_zarr` (consolidated metadata) and Elements with `write_elem` to the key `x` (not consolidated).
The variants (`v3_unsharded`, `v3_unconsolidated`, `v3_zstd`, `v3_blosc`, `v3_gzip` and `v3_none`) hold a few of the cases and are listed in `tests/testthat/fixtures/zarr/manifest.json`.
